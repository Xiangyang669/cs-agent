# 多 Agent 智能客服编排系统（cs-agent）

> 一个把「该不该转人工」这件事**做成可量化治理**的客服 Agent。
> LangGraph 显式条件边编排 · 双重判定 · 自建业务后端与故障注入 · 真挂起人工接管 · 110 条人工复核评测集

**仓库**：<https://github.com/Xiangyang669/cs-agent>

---

## 这个项目要解决什么

客服系统最核心的判断是一句话：**这件事该不该交给人**。而它有两个天然的坑：

**坑一：口径里有一部分是「规则做不到」的。**
硬条款（「重复扣费」「欺诈」「法务」）关键词一匹配就中；软条款（「这课我死活上不了，钱白花了」）**一个关键词都没有**。所以「为什么不用规则」不该是一句主观判断——**它应该是一张能跑出来的对照表**。

**坑二：两个指标天然对冲。**
漏判率（该转没转，最高危）与误转率（不该转却转了，烧成本）是一对跷跷板：**一律转人工能把漏判刷到 0，一律不转能把误转刷到 0**。所以绝不能只报一个「准确率 95%」。

**于是这个项目的命题是：治理的可量化。**

## 实测结果（核心证据）

**评测集：110 条，全部经人工逐条复核。** 4 配置 × 6 场景 × 7 指标，真跑模型并逐条缓存响应使矩阵可复现。
完整报告见 **[ACCEPTANCE.md](ACCEPTANCE.md)**。

### 硬条款 vs 软条款 —— 「为什么不用规则」的答案

| 条款类型 | 规则版路由准确率 | 规则版漏判率 | LLM 版路由准确率 | LLM 版漏判率 |
|---|---|---|---|---|
| **硬条款**（S3） | 1.000 | 0.000 | 1.000 | 0.000 |
| **软条款**（S5） | **0.000** | **1.000** | **1.000** | 0.000 |

> 两类样本来自同一份评测集、被同一张图处理，**唯一变量是分流策略**。

### 消融：每一档各贡献了什么（以业务故障 S4 为例）

| 配置 | 比上一档多了什么 | 路由准确率 | 漏判率 | 谎报率 |
|---|---|---|---|---|
| `R` | 规则分流 | 0.000 | 1.000 | 0.500 |
| `L` | 换成 LLM 分流 | 0.000 | 1.000 | 0.500 |
| `L+G` | **加终判守卫** | **1.000** | **0.000** | **0.000** |
| `L+G+H` | 加真人工接管 | 1.000 | 0.000 | 0.000 |

> 只加了一个守卫节点，三个指标同时从最差翻到最好。

### 一个「反过来」的发现

**S2（缺字段）上，LLM 版反而比规则版弱：0.889 vs 1.000。**
模型会把「我的课程打不开了」这种隐含个人情境的说法判成通用咨询，于是**该追问却不追问**。
这条缺陷**没有任何一条验收判据覆盖它**——判据是按「不能漏判高风险」设计的。

## 架构

```
用户消息 → ① 分流（Triage）← 可替换：规则版 / LLM 版
              │
              ├─ 高风险信号 ──────────────────────→ ⑥ 人工接管
              ├─ 缺信息 ──→ ② 追问 ──→ 本轮结束
              │              └─ 追问满 2 次 ─────→ ⑥
              ├─ faq ─────→ ③ 知识子图 ─┐
              └─ 订单/退款 → ④ 业务子图 ─┤
                                         ▼
                                   ⑤ 终判守卫
                              ┌─────────┴─────────┐
                         证据够              不足/故障
                              ▼                   ▼
                         ⑦ 回复              ⑥ 人工接管
                                               （真挂起）
```

**三个结构点：**

1. **两次判定，但不是同一件事。** 分流在**入图前**只能看用户说了什么；守卫在**拿到证据后**才判。⚠️ 而守卫**并不判断「该不该转人工」**——它只读 `faults_hit` / `evidence` / `business`，回答的是「**我查到的这些能不能用**」。
2. **配置的差异全在「建图那一刻」定完。** 守卫关掉时节点**真的不建**；人工接管关掉时绑的是另一个函数。图建出来之后，运行时没有任何一处 `if 配置`。
3. **转人工是真挂起。** 检查点落盘 → `interrupt()` → 人工回话 → 同一个 `thread_id` 从断点续跑。

## 快速开始

```bash
pip install -r requirements.txt
python -m pytest -q                        # 232 个测试

# 跑一遍评测，重新生成 ACCEPTANCE.md
python -m csagent.evaluation.run_eval
```

LLM 用 DeepSeek（任意 OpenAI 兼容端点均可），key 从环境变量 `DEEPSEEK_API_KEY` 或 `.env` 读。

```python
from csagent.graph import build_graph, run_ticket
from csagent.memory.checkpointer import memory_checkpointer
from csagent.retrieval import StubRetriever
from csagent.types import RunConfig

graph = build_graph(StubRetriever(), checkpointer=memory_checkpointer(),
                    guardrail=True, hitl=True)
cfg = RunConfig(triage="rules", guardrail=True, hitl=True, faults=())
state = run_ticket(graph, "你们重复扣费了两次，我要投诉！", cfg, thread_id="t1", history=[])
# → state["suspended"] == True，图停在人工接管节点
```

## 业务后端与故障注入

后端是**自建的 SQLite**（订单 / 支付 / 权限 / 受限账户四张表 + 种子数据），并内置**四类故障注入**：

| 故障 | 注入方式 | 期望行为 |
|---|---|---|
| 超时 | **真的 `sleep`** 0.2s（瞬间返回的「超时」与成功无从区分） | 守卫判「证据不足」→ 转人工 |
| 返回冲突 | 订单表说 paid、支付表说 unpaid | 判「数据冲突」→ 转人工 |
| 权限不足 | 返回受限状态、**空 rows**（不许从"空"推断"没买过"） | 判「无法确认」→ 转人工 |
| 脏数据 | 字段残缺（`amount: "N/A"`、`order_id: None`） | 判「数据不可信」→ 转人工 |

**为什么自建后端不是软肋**：真实系统里超时/冲突/脏数据只能碰运气遇到；自建后端让它们变成**可复现的实验条件**——这是唯一能真正验证降级路径的做法。

## 已知边界（诚实清单）

- ⚠️ **提示词在见过评测集之后修订过一次**，所以 LLM 的分数偏乐观。换一份没见过的样本重测，分数很可能更低。规则版没有这个问题。
- ⚠️ **判据「误转率 ≤ 20%」本轮是空过的**——四档配置都是 0.000，因为没有哪一档倾向转人工。它的价值要等将来调参才体现。
- ⚠️ **评测集有两个方向的偏差**：S1/S2/S6 复用了规则词表已有的说法（**偏向规则版**），S5 软条款样本正是按「规则做不到」挑的（**对规则版不利**）。两个方向都有，所以不能只报一侧。
- **人工接管里的「人工」是注入的一条消息**，不是真客服在打字；坐席端 UI 不在范围内。
- **人工接管无超时策略**——审批人一直不回复，会话就一直挂着。
- **本项目里没有任何真正的写操作**，全部是查询。
- 检查点用 SQLite，并发/多实例时会成瓶颈。

## 工程过程

17 个任务、逐任务裁定与**端到端跑出的 8 个真缺陷**（D6–D15）+ 独立评审查出的 3 条（C1 / I1 / D16）全部修复，记录见执行台账。

**这些缺陷的共性是：每个模块自己的单元测试全绿，接起来才炸。** 典型的几条：

- **谎报率判据失效**——原判据是关键词正则，而故障下回复渲染的是英文状态和 `"N/A"`，一个都匹配不上：**系统明明在谎报，矩阵却记成 0.000**。改成「按数据本身判」后谎报率 = 0.500，正是四种故障的真实分布。
- **评测集与业务库对不上账**——评测集引用的 36 个订单号在业务库里不存在。症状看起来像「系统路由错了」，真因是查不到 → 守卫正确地转了人工。
- **SQLite 跨线程**——图在别的线程跑节点而复用了调用方给的连接，抛错后被降级机制**静默吞成「查不到」**。
